# Naslos audit — 2026-09-19

- **Baseline:** `origin/master` = `85ae874` (PR #23 merged; the dev-endpoint
  removal is in scope). Working tree content == that commit.
- **Live target:** cluster on `192.168.1.117`, helm revision 16 — `naslos-api`
  `0.1.0-r4`, `naslos-agent` `0.1.0-r3`, `naslos-ui` `0.1.0-r5`, Traefik
  hostPort 80/443, Authelia 4.39, `naslos.local`.
- **Method:** static review, automated scanners (gitleaks, trufflehog,
  govulncheck, gosec, npm audit) and read-only live inspection. Active
  verification is partial (see coverage).
- **No secret values appear in this report.** Findings cite key names, files and
  lines; rotate anything flagged out of band.
- Existing reports: `docs/SECURITY-AUDIT.md` (2026-09-14, pre-fix, superseded
  where noted) and `docs/CODE-REVIEW.md` (CR-01…CR-43, living list).

## Executive summary

| Severity | Count |
| --- | --- |
| Critical | 0 |
| High | 4 |
| Medium | 14 |
| Low / Info | 10 |

The **authentication model is now sound**: no unauthenticated listener exists,
owner routes require the proxy secret + trusted source + `Remote-*`, admin routes
require `naslos_admins`, and 2FA applies to admins on every path (verified live:
anonymous `/api/*` → 302, pod without secret → 401, agent without token → 401,
`:30080` refuses). The remaining risk is concentrated in **credential hygiene,
one live backup misconfiguration, and supply-chain/Kubernetes hardening**.

Top risks in plain language:

1. **A live LDAP credential is committed** (`openldap.bindPassword` in
   `charts/naslos/values-vm.yaml`) and deployed verbatim; the repo is private, so
   it is insider-exposure rather than internet-exposure, but it is a working
   directory-admin credential for `cn=naslos-service`.
2. **Received backup chunks are written to the 64 MiB shares volume**, not the
   receive dataset, because the live release runs `buddy.enabled=false` while the
   peer API is active. Backups survive only until the PVC is recreated.
3. **18 reachable Go vulnerabilities** flow in through `helm.sh/helm v3.16.0`,
   `containerd v1.7.12`, `docker v25.0.6` and `moby/spdystream v0.4.0` — the
   spdystream one is on the terminal-exec code path.
4. **No network policy and an unenforced CNI**: the privileged, hostNetwork agent
   on `:9090` is reachable from every pod; the token is the only control.

## Findings

### High

**AUDIT-H1 — Live LDAP service credential committed and deployed.** (SL) —
**RESOLVED 2026-09-19.** The password is no longer in values: the Authelia config
reads it from the `naslos-openldap` Secret (key `service-password`) via `lookup`,
values default to empty with a fail-closed guard, and the VM profile has no
`bindPassword`. The credential was rotated (Secret patch + a bootstrap re-run,
which applies the new SSHA) and verified at helm revision 22: the new value binds
(`ldapwhoami` → `cn=naslos-service,…`), the old committed value is rejected, and
the full Playwright suite is 35 passed (Authelia login + LDAP-backed pages).
Original finding below.

`charts/naslos/values-vm.yaml` set `openldap.bindPassword: CHANGE_ME_SERVICE_PASSWORD`;
`helm -n naslos get values naslos` confirms that exact value is deployed, and
Authelia/the API bind with it. Anyone with repo read (or a deployed `values`
dump) can bind as `cn=naslos-service,ou=services,dc=naslos,dc=local`, the
identity the API uses to read users and set passwords. It is also a weak
placeholder. *Fix:* rotate to a random value in the `naslos-openldap` Secret,
set `openldap.bindPasswordSecret`-style indirection (or `existingSecret`), and
remove the literal from values.

**AUDIT-H2 — Buddy receive path is misconfigured; chunks land on the 64 MiB
shares volume.** (OPS/SEC) — **RESOLVED 2026-09-19**:
`values-vm.yaml` now sets `buddy.enabled=true` and
`receiveHostPath: /var/mnt/test/naslos-buddy`, so the existing dataset is mounted
at `BUDDY_RECEIVE_PATH`; the API's init container chowns it to 65532. Verified at
helm revision 21: the pod mounts the dataset, the backup suite passes, and
`zfs list test/naslos-buddy` shows the received chunks (96K) on the dataset
instead of the shares PVC. Original finding below.
Live values: `buddy.enabled=false`, `buddy.receiveHostPath=""`. The chart only
sets `BUDDY_RECEIVE_PATH` (and mounts the receive dataset) when
`buddy.enabled=true` (`charts/naslos/templates/api-deployment.yaml:169,215,266`),
so `api/internal/server/server.go:131` falls back to
`/var/lib/naslos/buddy`, which is inside `api.sharesConfig` (64 MiB, mounted at
`/var/lib/naslos`). Received encrypted chunks therefore share the config volume,
will hit capacity on a real dataset, and are lost when that PVC is recreated.
The E2E receiver tests pass only because their payload is tiny. *Fix:* either
disable the peer API when `buddy.enabled=false`, or require
`buddy.receiveHostPath` and mount it; separate the receive dataset from the
shares volume.

**AUDIT-H3 — 18 reachable Go vulnerabilities.** (SUP)
`govulncheck ./...` (api): 18 reachable from 5 modules, notably
`helm.sh/helm/v3@v3.16.0` (GO-2025-3888/3887/3602/3601, fixed ≥3.18.5 — CR-05),
`github.com/moby/spdystream@v0.4.0` (GO-2026-4958, fixed v0.5.1; reached via
`api/internal/server/websocket.go:431` terminal exec),
`golang.org/x/crypto` openpgp (GO-2026-5932, unmaintained),
`containerd v1.7.12` and `docker v25.0.6` (multiple, fixed 1.7.27–1.7.35 /
25.0.13). Most containerd/docker traces are transitive through Helm's k8s
client and not realistically reachable, but the Helm and spdystream ones are.
*Fix:* bump `helm.sh/helm/v3` to ≥3.18.5 and re-run govulncheck; the spdystream
bump follows from the k8s/helm dependency graph.

**AUDIT-H4 — Grafana admin password is a committed default.** (SL) —
**RESOLVED 2026-09-19 by removal**: the Grafana subchart is disabled
(`grafana.enabled: false`) and the literal `adminPassword` is gone. It was
ClusterIP with no IngressRoute, so never LAN-reachable, but the credential was in
the repo and every Helm release. Re-enabling it requires a credential from a
Secret, never a literal in values.

### Medium

**AUDIT-M1 — Talos PKI and cluster secrets recoverable from local git history.**
(SL) `gitleaks detect` on the repository reports `private-key` and cluster-secret
hits in `bootstrap/out/controlplane.yaml`, `bootstrap/out/worker.yaml`,
`bootstrap/out/talosconfig` and `bootstrap/vm/talosconfig-pod`. They are only in
local Cline/Kilo checkpoint refs (`refs/cline/checkpoints/*`): `git ls-remote
origin` shows no such ref and no branch contains them, and the current
`bootstrap/vm/talosconfig-pod` blob (`0dea67f4…`) differs from the committed one
(`af02e3a2…`), so the leaked material is the retired cluster's. *Fix:* delete
`refs/cline/checkpoints/*` and `git gc --prune=now`; never `git push --mirror`
from this clone; confirm the old cluster is destroyed.

**AUDIT-M2 — Local secret files are world-readable.** (SL)
`bootstrap/vm/controlplane.yaml`, `talosconfig`, `talosconfig-pod` and
`ui/tests/.auth/admin.json` are mode `0644` (the admin session cookie and the
node admin kubeconfig). `ui/.env.playwright.local` is correctly `0600`. *Fix:*
`chmod 600`; the chart already sets 600 for the in-cluster mirrors (CR-15).

**AUDIT-M3 — Authelia `jwt_secret` regenerates on every render, and secrets live
in a ConfigMap.** (SL/OPS) `charts/naslos/templates/authelia-config.yaml` uses
`randAlphaNum 32` for `jwt_secret`, so every `helm upgrade` writes a new
ConfigMap, invalidating all sessions (and storing a fresh secret in the release
secrets). The LDAP bind password and `jwt_secret` are rendered into the
`authelia-config` ConfigMap rather than a Secret, so anyone with `get configmap`
reads them; the Helm release secrets (`sh.helm.release.v1.naslos.v7..v16`)
retain every historical value including `naslos-tls`. *Fix:* `lookup`-persist the
`jwt_secret` (same pattern as `naslos-proxy`), move secret material to a Secret,
and prune old release secrets.

**AUDIT-M4 — No NetworkPolicy, and flannel does not enforce one.** (K8S)
`kubectl get networkpolicy -A` → none. The agent is `hostNetwork` +
`hostPID` + `privileged` with hostPaths `/`, `/dev`, `/run`, `/var`
(`charts/naslos/templates/agent-daemonset.yaml`) and listens on `:9090`; any pod
can reach it (verified: the terminal pod gets 401 without the token, i.e. the
route is open and only the token guards it). *Fix:* a policy-enforcing CNI
(Cilium/Calico) or a host firewall rule allowing only `naslos-api` → `:9090`,
plus a NetworkPolicy for documentation/portability.

**AUDIT-M5 — Unused cluster privilege on the agent.** (K8S)
`clusterrole/naslos-agent` grants `get/list/watch` on `nodes`, `pods`,
`pods/log` cluster-wide, but the agent never calls the Kubernetes API (it
`chroot`s the host). *Fix:* drop the ClusterRole/Binding (CR-37).

**AUDIT-M6 — Namespace pod security is `privileged`.** (K8S)
`namespace naslos` carries `pod-security.kubernetes.io/enforce: privileged`
(needed by agent/terminal), which also lets any compromised workload in the
namespace escalate. *Fix:* scope the exemption (separate namespace for the
privileged DaemonSets, or PSA `baseline` + explicit `privileged` labels on the
two workloads) — CR-37.

**AUDIT-M7 — API server has no `ReadHeaderTimeout` (Slowloris).** (CQ)
`api/internal/server/server.go:340` builds `http.Server` with only `Addr` and
`Handler`; gosec G112. *Fix:* set `ReadHeaderTimeout` (and
`ReadTimeout`/`IdleTimeout`).

**AUDIT-M8 — Config files with secrets are written `0644`.** (CQ)
`internal/notifications/manager.go:51` writes `notifications.json` (which holds
the ntfy `authToken`) mode 0644; `shares/manager.go:87`,
`server/buddy_schedules.go:179`, `buddy/store.go:1095`, `buddy/peers.go:158`
write 0644, and several `MkdirAll(…, 0755)` create world-readable dirs. The
container is non-root (`65532`) so the practical reach is limited to other
processes in the pod, but it contradicts the 0600 the identity files already use.
*Fix:* 0600/0700 for anything with a token or key.

**AUDIT-M9 — Buddy store path handling flagged by taint analysis.** (CQ)
gosec reports G703/G304 on `api/internal/buddy/store.go` (many sites) and
`buddy/http.go`. Paths are built from the configured root plus chain/index
values; the risk is a crafted chain name escaping the root. `chunkName(index)`
and the chain directory come from manifests and requests. *Fix:* validate chain
names/indices against a strict pattern (the `walkbounds_test.go` harness shows the
intent) and prefer `os.Root`.

**AUDIT-M10 — Mutable image tags, `IfNotPresent`, no digests, plain-HTTP
registry.** (SUP) Live values pin `0.1.0-rN` by tag with `digest: ""` and
`pullPolicy: IfNotPresent`; the registry is `192.168.1.2:30095` over HTTP (no
TLS), so a tag can be re-pointed and a node may keep a stale image. *Fix:*
digest-pin (`image.digest` already exists in the chart), enable TLS/auth on the
registry, and never retag (CR-38/CR-40).

**AUDIT-M11 — 11 dev-dependency advisories (1 high).** (SUP)
`npm audit` full: `svelte ≤5.55.6` (six SSR/spread XSS advisories), `vite/esbuild`,
`cookie` via `@sveltejs/kit`. `npm audit --omit=dev` → 0. The build is
`adapter-static`, so the SSR XSS advisories are not reachable at runtime, but the
toolchain should be bumped. *Fix:* upgrade Svelte 5 and Vite (CR-08/CR-31).

**AUDIT-M12 — No CI; the security scans are manual.** (OPS) —
**Partial**: `scripts/audit.sh` now packages the sweep (go vet/test, govulncheck,
gosec, npm audit, svelte-check, helm lint, gitleaks) and is runnable by hand; the
GitHub Actions workflow that was added with it (`421711a`) was **removed at the
operator's request**, so nothing runs it automatically yet. *Fix (later):* wire
`scripts/audit.sh` into CI when the repository is ready for it (CR-09).

**AUDIT-M13 — `storage.zfsLocalPV` renders nothing usable.** (OPS)
Values enable `zfsLocalPV` with `poolName: naslos-pool`, but the only
StorageClass is `local-path` (rancher) and the shares PVC uses
`storageClassName: ""` (default local-path). The host pool is `test` (per the
handoff), not `naslos-pool`. The ZFS provisioner is not installed. *Fix:* either
drop the setting or install/point the provisioner at the real pool.

**AUDIT-M14 — Documentation and recovery gaps.** (DOC/OPS)
`docs/SECURITY-AUDIT.md` still describes the pre-fix posture (unauthenticated
agent/API) without a superseded banner. The recovery runbook covers Authelia
misbehaviour generally but not loss of the TOTP device / Authelia SQLite or the
rotation of the LDAP bind secret — now the only way back in is cluster access.
*Fix:* add a superseded banner, and an "operator locked out" runbook section
(inspect the Authelia PVC, passkey reset, `helm rollback`).
