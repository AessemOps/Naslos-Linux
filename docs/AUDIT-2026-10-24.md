## Executive summary

The single exploitable auth-boundary defect in the Rust port was the fail-open
CIDR check (`auth.rs`), which is now fail-closed and covered by tests. The two
lost Go controls that mattered most were restored: the WebSocket `Origin` check
(NAS-009) and the member-of/authenticated LDAP posture. Cross-origin state
changes are now refused by a CSRF layer that does not break the CLI/API.

The most serious **remaining** findings are architectural, not bugs:

1. **Legacy apps can still mount the shared `naslos-datasets` RWX volume**
   (High, D3/F1). New installs are isolated (per-app namespace + per-dataset
   PV/PVC); legacy records need a reinstall/migration, documented in
   `docs/datasets-isolation.md`.
2. **Chart provenance is pinned but not signed** (High, D6): the official
   source is pinned to an audited commit and any source can set a verified SHA,
   but a compromised repository host could still serve a different tree at that
   SHA (no signature check). Privileged installs need explicit consent (D8). The
   Helm identity can no longer take over routing/certs (D1 fixed).

These are recorded below with evidence and a proposed fix. They are **open**,
not silently accepted; they need the operator's design decision before the next
release. Everything else classified High in this register is fixed on this
branch or explicitly listed as open.

## Batch 13 (branch `fix/clean-install-followups`) — clean-install drill

The 0.2.1 clean install (installer v0.2.3, Talos v1.14.1) surfaced two
follow-ups:

- **Empty catalog after install:** the official source was seeded but never
  synced until an admin clicked Refresh. The API now runs `refresh_all()` at
  startup and stores the rebuilt catalog (failures are logged, not fatal).
- **Buddy store exposure with Buddy disabled:** the installer profile does not
  set `BUDDY_RECEIVE_HOST_PATH`, so the registry could not see the inherited
  `test/naslos-buddy` dataset. Registration now rejects any path that is,
  contains, or sits inside a dataset named `*/naslos-buddy` (checked from the
  agent's live dataset list), with a unit test.
- **Exposed app routes timed out:** the IngressRoute and copied TLS Secret were
  created correctly, but Traefik's `naslos-workload-egress` policy did not allow
  the per-app namespaces. Both workload egress policies now allow
  `naslos.local/apps=true`; verified live with a TLS-exposed FlareSolverr
  (`HTTP 200`) after applying the rendered policy. The live cluster carries
  this one policy patch until the 0.2.2 chart is installed.

Drill results: Playwright 48 passed / 5 skipped; API health+readiness green;
private dataset registered and removed; a test app installed into
`naslos-app-1` with a bound `naslos-app-data` PV/PVC, a copied `naslos-apps-tls`
Secret and an IngressRoute, reached through Traefik at
`https://flaresolverr.naslos.local` (HTTP 200), then uninstalled cleanly
(release, claims and registry attachment removed); the record persisted its
`namespace` and `datasets`. Catalog refresh was the only missing first-run
step. The live namespace policy was patched for the route drill; 0.2.2 carries
the same rule in the chart.

The TLS `naslos-tls` TLSOption and RuntimeDefault seccomp (batch 12) are in the
0.2.1 release and were included in the drill.

## Batch 11 (branch `feat/per-app-datasets`)

Option A groundwork (D3/F1):

- **Managed dataset registry:** `GET/POST /api/datasets/registry` and
  `DELETE /api/datasets/registry/{name}`. Paths must be mounted ZFS datasets
  below `/var/mnt`, normalized, and must not overlap the Buddy store; `shared`
  requires an explicit `warningAcknowledged`. The UI page (`/datasets`) lists
  records and shows a red shared-dataset warning plus a second checkbox, and the
  install modal selects one registered dataset.
- **Per-app namespaces:** the chart creates a fixed baseline/privileged pool
  (`apps.isolation.*`) with PSA, quota/limits, a default-deny NetworkPolicy,
  RoleBindings to `naslos-helm-workloads` and `naslos-api-app-isolation`, and the
  `naslos-app-data` StorageClass. The API assigns a free namespace to each new
  install (`APPS_NAMESPACE_POOL`/`APPS_PRIVILEGED_NAMESPACE_POOL`) and records it.
  Fresh installs set `apps.datasets.enabled=false`, so no shared `/var/mnt` PVC
  exists at all.
- **Per-dataset claims:** the API creates one PV/PVC per selected registry
  dataset (`hostPath` = that dataset only), passes `datasetsClaim` to the chart
  (privileged apps get the specific `hostPath`), copies the domain TLS Secret
  into the app namespace for the IngressRoute, and removes the claims on
  uninstall. A private dataset cannot be attached to a second app; a shared one
  can (with the recorded warning).
- Unit tests cover path normalization, Buddy overlap, shared acknowledgement and
  registry round-trips; the rendered-chart gate checks the namespace pool,
  PSA labels, ClusterRoles and pool env.

**Catalog caveat:** the claim's root is the selected dataset, so charts whose
values assume `/var/mnt`/`/data/<pool>/<dataset>` must be pointed at the dataset
root. Existing records stay on the shared PVC until reinstalled. See
`docs/datasets-isolation.md`.

## Batch 10 (branch `fix/audit-batch-10`)

Tenth remediation batch (D3/F1 groundwork):

- Added `docs/datasets-isolation.md`: current shared-root model, threat model,
  why per-app PVCs in one namespace are not a boundary, options A (per-app

This does not close D3/F1: the per-app namespace/PV migration is the remaining
work.

## Batch 6 (branch `fix/audit-batch-6`)

Sixth remediation batch:

- **App-chart trust boundary:** Helm installs now run as a dedicated
  `naslos-helm` ServiceAccount (token Secret mounted into the API) whose
  namespaced Role in `naslos-apps` excludes `traefik.io`, `cert-manager.io` and
  RBAC. The API keeps its own identity for routes, certificates and exec, so a
  malicious chart can no longer hijack the platform host or issue certificates
  (D1 fixed, D4 partially fixed). A chart that ships its own route now fails
  with 403 instead of silently taking over.

## Batch 5 (branch `fix/audit-batch-5`)

Fifth remediation batch:

- **LDAP credential:** the API reads the bind password from a mounted file
  (`LDAP_BIND_PASS_FILE`), so forked `helm`/`kubectl`/`talosctl` children no
  longer inherit it; an unreadable file fails startup instead of falling back to
  an empty password (F16).
- **Health notifications:** a 60 s watcher notifies on ZFS pool/agent health
  transitions (H6), using the existing `zfs_health`/`disk_failure` events and
  transition-only de-duplication.
- **API hardening:** read-only root filesystem with a writable `/tmp` for Helm
  and kubeconfig (D13).

## Accepted-risk / sign-off list

These are deliberate design properties or previously accepted risks that the
audit did not overturn. Each needs an explicit sign-off line in the release PR:

- **D15** API `pods/exec` covers the workload namespace; the API also mounts the
  Talos admin config. This is the documented crown-jewel chain; narrowing it
  needs a dedicated terminal namespace/SA.
- **F15/AUDIT-M4** agent `:9090` is host-networked and the Cilium host firewall
  is off by default. Mitigations: bearer token + TLS; a live host-firewall
  rollout needs the node label and an out-of-band recovery path.
- **F18** the release namespace enforces PSA `privileged` because the API mounts
  a hostPath. The alternative is moving UI/OpenLDAP/Authelia to a baseline
  namespace.
- **G13/AUDIT-M10** the VM overlay uses the plain-HTTP private registry with
  mutable tags. The release pack is digest-pinned; the VM path is not.
- **E18** Playwright admin session material lives under the gitignored
  `ui/tests/.auth` (0600).

## Accepted-risk candidates for the 0.2.1 clean install

These are not silently dropped; each line must be signed off in the release PR
before tagging:

- **D6 (signature):** the catalog is commit-pinned with a fail-closed checkout,
  but commit/tag signatures are not verified. Closing this needs a signing key
  and a signed-tag workflow in `NaslosCharts` (the catalog owner), not a change
  in this repository. The commit pin still prevents a moving branch.
- **D19 (app values at rest):** chart values may contain credentials and are
  stored in `apps.json` (0600 on the state PVC) and returned to the owner UI.
  The API has no at-rest encryption key; accept for 0.2.1.
- **F20 (LDAP `olcSecurity`):** TLS is required by the API/Authelia/nss
  configuration and the network policy; the database-level `olcSecurity` is
  unset to avoid breaking the `ldapi://` bootstrap. Accept until a live drill
  proves the stricter setting.
- **F21 (local-path `0777`):** required so arbitrary app UIDs can write their
  PV directories on a single-node appliance. Accept with node-level trust.
- **C15, H17–H19:** low-severity buddy `/status` audience and resume
  efficiency items; tracked open.

controlled VM drills were not run. They are the release gate for 0.2.1:
