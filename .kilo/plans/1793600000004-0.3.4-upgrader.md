# 0.3.4 upgrader patch plan

Status: implemented (code + tests) · Target release: **0.3.4** · Release/deploy
steps below still pending
Repos: `Naslos-Linux` (API, chart, tests) + `Naslos-Installer` (version
parity only).

## Evidence from the live 0.3.1 → 0.3.3 attempt

The RBAC `patch jobs` fix (already on `master`, `8a728a2`) let the API create
the operation Job. The Job then failed twice:

1. `talosctl --talosconfig /var/run/secrets/talos.dev/config etcd snapshot …`
   exited 1 with `nodes are not set for the command`. The mounted talosconfig
   has an `endpoints` entry but no node list, and `run_talos()` only passes
   `--talosconfig`.
2. Every progress write logged:
   `apply -f - --server-side … failed to create typed patch object
   (naslos/naslos-system-operation; /v1, Kind=ConfigMap):
   .stringData: field not declared in schema`.
   `Writer::save()` sends `stringData`, which is not part of the server-side
   apply schema; the UI therefore never receives the operation status.

The failed operation did not apply a Helm/Talos change; it stopped at the
snapshot step. A new operation can be started once the API is fixed.

## Fixes

### 1. ConfigMap status uses `data` (API `rust/api/src/upgrade/status.rs`)

- Build the ConfigMap object with `"data": {"state": <json>}` instead of
  `"stringData"`.
- Extract `configmap_object()` so a unit test asserts `data.state` exists and
  `stringData` is absent.
- Keep the local marker write first; a status write failure remains a warning.

### 2. Give the upgrader Job Talos nodes (API + Job spec)

- Add `TalosClient::nodes()` (the API already resolves nodes from
  `TALOS_NODES` or the talosconfig endpoints).
- Add `talos_nodes` to `JobOptions` and set
  `TALOS_NODES` in the Job env (`system.rs::job_spec`).
- `server/system.rs` reads the nodes from `state.talos`, and rejects the
  operation with a clear precondition when there is no Talos client/nodes.
- `upgrade/ops.rs::run_talos()` appends `--nodes <csv>` when `TALOS_NODES` is
  set. Extract `talos_args()` so the argument order is unit-tested.
- This fixes etcd snapshot and the Talos upgrade path; Kubernetes/Naslos
  operations that call `run_talos` get the same fix.

### 3. Keep the RBAC `patch jobs` fix in the 0.3.4 chart

- `charts/naslos/templates/system-upgrade.yaml` already grants
  `get/list/create/delete/patch` to `naslos-api-system` on `master`.
- The 0.3.3 chart still has the old verbs; 0.3.4 must ship the new chart.
- `scripts/audit.sh` already asserts the rendered Role can patch jobs.

## Tests

- `upgrade::status`: ConfigMap object uses `data`, no `stringData`.
- `system::tests`: `job_spec` includes `TALOS_NODES` and the value; existing
  lockdown assertions still pass.
- `upgrade::ops`: `talos_args` includes `--talosconfig` and `--nodes` in the
  expected order; no nodes means no `--nodes` flag (the API rejects that case).
- `server/system` tests (or a pure helper): missing Talos nodes is a
  precondition error.
- `helm template`/`scripts/audit.sh`: Role has `patch`; Job template remains
  admission-policy compliant.
- Playwright `system.spec.ts` and the live upgrade drill.

## Release and deployment

1. Bump `Naslos-Linux` chart/UI to 0.3.4 and `Naslos-Installer` to 0.3.4
   (version parity); merge the fix.
2. Tag `v0.3.4`; release the digest-pinned pack and let the workflow dispatch
   the installer. Verify `naslos-install-pack-0.3.4.tar.gz` is attached.
3. Deploy the **0.3.4 API image** to the current 0.3.1 node with the live
   values (same API-only path used for 0.3.3). The chart remains 0.3.1 so the
   updater offers 0.3.4.
4. Verify `/api/system/updates` returns 0.3.4 as available/allowed and
   `/api/metrics` still works.
5. Retry the web upgrade. The Job should now write a `data` status, take the
   etcd snapshot with `--nodes`, and run Helm. The 0.3.4 chart applies the
   RBAC patch so later upgrades keep working.

## Recovery notes

- The failed `0.3.1 → 0.3.3` Job can be left to its TTL or deleted; its
  operation id is different, and `Writer::load_or_init` only blocks an
  *active* operation.
- If the failed ConfigMap is absent (the old `stringData` writes failed), the
  new operation still starts; the UI shows the new status once the fixed
  writer runs.
- No Helm/Talos change was applied by the failed attempt, so there is nothing
  to roll back.

## Risks

- A multi-node cluster needs all node addresses in `TALOS_NODES`; the API
  passes the comma-separated list.
- `state.talos` is optional in degraded API mode; the new precondition must
  fail closed with a clear message rather than creating a Job that cannot
  snapshot.
- The status JSON is small; `data` is sufficient (no binary data).
