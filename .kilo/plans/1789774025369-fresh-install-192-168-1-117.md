# Talos upgrade on 192.168.1.117 + post-upgrade test

## Context

The fresh install on the new VM is done and recorded in `AI_Handoff.md`: Talos
**v1.14.0** (Naslos ISO, ZFS extension), chart revision 2, all images `0.1.0-r1`,
all pods Running, `/api/ready` 200, Playwright **16 passed / 5 skipped** (the skips
are the bare-install gaps: no ZFS pool, no LDAP users). The old .96 VM is powered
off. There is **no `make` target** for a Talos upgrade; the documented interface is
a bare `talosctl upgrade` (`docs/bootstrap.md` §Upgrades, `docs/deployment.md`
:286, NFR-2 in `docs/spec.md`).

A `talosctl upgrade` installs the target release — with the ZFS extension baked in
from the **same Image Factory schematic** — to the inactive system partition,
reboots, and `zfs-service` re-imports pools on the new boot. STATE (machine config,
cluster PKI) is preserved, so no re-apply is needed. This is the low-risk path:
only data placed on the **EPHEMERAL** partition is lost
(`docs/shares.md:251`).

Pinned schematic: `4dd8e3a8b6203d3c14f049da8db4d3bb0d6d3e70c5e89dfcc1e709e81914f63c`
(extension-only, so it should build for any Talos 1.x — verify, don't assume).

**VNC is not needed for this.** All of it goes through the Talos/k8s APIs, which
the runbook uses; keep VNC only as the console *you* would open if a node ever fails
to come back (ISO boot order, kernel panic). I cannot drive a GUI from this
environment.

## Task 0 — permissions

This work needs `talosctl`, `kubectl`, `curl` and (only if the runbook is committed)
`git`. The current sandbox denies them (read-only allowlist only), which is why the
upgrade could not be executed in the planning turn. Either grant those commands or
run the commands below manually and feed back the output.

## Task 1 — pre-flight and version discovery

```bash
export TALOSCONFIG=bootstrap/vm/talosconfig
talosctl version --nodes 192.168.1.117 --endpoints 192.168.1.117
talosctl get extensions --nodes 192.168.1.117 --endpoints 192.168.1.117
talosctl health --nodes 192.168.1.117 --endpoints 192.168.1.117
kubectl get nodes
kubectl -n naslos get pods

# newest stable release the factory offers
curl -s https://factory.talos.dev/versions | jq -r '.versions[]?' | head -20
# what the schematic actually builds (extensions + versions)
curl -s https://factory.talos.dev/schematics/4dd8e3a8b6203d3c14f049da8db4d3bb0d6d3e70c5e89dfcc1e709e81914f63c
```

Choose the target: the newest stable release for which the schematic resolves.
Confirm the installer tag exists before upgrading — a missing extension version
fails the factory build and the node would pull nothing.

Record the baseline for the post-upgrade diff: current version, extension list, node
state, pod list, `/api/ready`, and `curl -s http://192.168.1.117:30080/api/volumes/zfs`.

## Task 2 — upgrade

```bash
export TALOSCONFIG=bootstrap/vm/talosconfig
talosctl upgrade \
  --nodes 192.168.1.117 --endpoints 192.168.1.117 \
  --image factory.talos.dev/installer/4dd8e3a8b6203d3c14f049da8db4d3bb0d6d3e70c5e89dfcc1e709e81914f63c:<TARGET_VERSION> \
  --wait
```

Single-node control plane: expect a few minutes of API downtime. Do **not** pass
`--preserve=false` (that clears STATE, i.e. the machine config and cluster PKI).

## Task 3 — post-upgrade test matrix

| Check | Command | Expected |
| --- | --- | --- |
| Release | `talosctl version --nodes … --endpoints …` | the target version |
| Cluster health | `talosctl health …` | all checks OK |
| Extension | `talosctl get extensions …` | `zfs` listed, same schematic lineage |
| Node | `kubectl get nodes` | `Ready`, same name/IP |
| Workloads | `kubectl -n naslos get pods` | api/ui/agent/samba/nfs/terminal/openldap/traefik/authelia/prometheus/grafana Running, no new restarts |
| API | `curl -s -o /dev/null -w '%{http_code}' http://192.168.1.117:30080/api/ready` | 200 |
| Agent + ZFS | `curl -s http://192.168.1.117:30080/api/volumes/zfs` | `[]` (no pool) — an agent error means the ZFS module/service did not come back |
| Owner gate | `curl -s -o /dev/null -w '%{http_code}' http://192.168.1.117:30080/api/users` | 200 (dev posture keeps `auth.disabled=true`) |
| Dashboard | `curl -s http://192.168.1.117:30080/api/dashboard` | metrics + `ens3 → 192.168.1.117` |
| UI suite | `cd ui && PLAYWRIGHT_BASE_URL=http://192.168.1.117:30080 npx playwright test` | **16 passed / 5 skipped** baseline — any new failure or a lower pass count is a regression |

If a pool exists by then, add the storage drill:

```bash
kubectl -n naslos exec deploy/naslos-terminal -- chroot /host /usr/local/sbin/zpool status
kubectl -n naslos exec deploy/naslos-terminal -- chroot /host /usr/local/sbin/zfs list
```

Pools must re-import automatically; one missing means `zfs-service` failed on the
new boot (`talosctl dmesg`, `talosctl get extensions`).

## Task 4 — rollback (only if needed)

Re-run the same `talosctl upgrade` with the previous version: Talos keeps the
previous image on the inactive partition. Data disks and local-path PVCs are
untouched in either direction.

## Task 5 — record the outcome

Append the result to `AI_Handoff.md` (new version, schematic, what passed, any
regression) and, if this becomes the standing procedure, land the runbook as
`docs/talos-upgrade-runbook.md` — the content is Task 1–4 above. Also worth noting
there: there is no `make upgrade-vm`, and the deploy script's config-gen reuse of
`bootstrap/vm/talosconfig` is correct for upgrades but wrong for re-installs.

## Risks

- **ZFS extension availability.** If the schematic cannot resolve for the target
  version, the node pulls nothing and the upgrade fails before touching anything;
  check first (Task 1).
- **Single node, no HA.** The control plane is down for the reboot; that is the
  expected, accepted downtime for a one-node appliance.
- **No pool exists yet**, so the ZFS re-import path is only *partially* exercised
  (module + service, not an actual pool). Creating a pool first (the pending step
  from the install) would make this test stronger — worth doing if you want the
  upgrade to prove the data path too.
- **Buddy is disabled** on this VM, so the upgrade does not touch backup state;
  enabling it (receive dataset + secrets) remains a separate step.
