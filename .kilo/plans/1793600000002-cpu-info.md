# CPU info (temperature, load per core) for 0.3.2

Status: proposed · Target release: **0.3.2**
Repo: `Naslos-Linux` (API collector, dashboard UI, spec/docs/tests).

## Goal

Extend the live system metrics and dashboard with CPU detail:

- model name and logical core count;
- overall usage from a real `/proc/stat` delta, plus 1/5/15-minute load;
- per-core usage (and frequency when `/proc/cpuinfo` exposes it);
- package/CPU temperature when the node exposes a thermal zone or a
  `coretemp`/`k10temp`-style hwmon; otherwise `null` and an explicit UI note.

## Facts

- The API already collects CPU usage, core count and load averages from the
  Talos API (`rust/api/src/talos.rs::cpu_metrics`) and publishes them through
  `SystemMetrics` / `/api/metrics` / `/api/dashboard` every 5 s.
- Talos exposes `/proc/stat`, `/proc/cpuinfo`, `/sys/class/thermal` and
  `/sys/class/hwmon` through `talosctl read`; the VM has no thermal zone, so
  temperature must be optional and must not fail the rest of the metrics.
- The dashboard already auto-refreshes every 5 s; no new endpoint is needed.
- `CpuMetrics` is the shared shape for `/api/metrics` and the dashboard view.

## Design

1. **Metrics model** (`rust/api/src/metrics.rs`): add to `CpuMetrics`
   `model: String`, `temperature_c: Option<f64>`, `per_core: Vec<CpuCore>`;
   `CpuCore { core, usage_percent, frequency_mhz: Option<u64> }`. Include the
   new fields in `dashboard_data()` (`temperatureC`, `model`, `perCore`,
   `loadAvg1/5/15`).
2. **Collector** (`rust/api/src/talos.rs`):
   - read `/proc/stat` twice ~200 ms apart and compute overall and per-core
     usage from the deltas (fall back to the cumulative single-read estimate if
     the second read fails);
   - parse `/proc/cpuinfo` for the model and per-processor `cpu MHz`;
   - discover temperature from `/sys/class/thermal/thermal_zone*/temp` and
     `/sys/class/hwmon/hwmon*/{name,temp1_input}`, accepting only CPU-like
     hwmon names (`coretemp`, `k10temp`, `zenpower`, `cpu`); cache the result
     for 30 s so missing hardware does not spawn a probe on every 5 s tick;
   - all temperature failures are non-fatal (`temperatureC: null`).
3. **UI** (`ui/src/lib/components/Dashboard.svelte`): add temperature and load
   to the CPU quick card and a CPU details card with model, load averages,
   temperature (or "not exposed on this node"), and one bar per core with usage
   and frequency. Data attributes for the Playwright assertions.
4. **Spec/docs**: extend FR-MET-03's CPU shape, add FR-MET-11 (per-core/load/
   temperature collection and graceful unavailability) and FR-MET-12 (dashboard
   rendering); update `docs/api.md`, `docs/operations.md`, `README.md`,
   `AI_Handoff.md`.
5. **Tests**: pure `parse_proc_stat`/`parse_cpuinfo`/temperature parsing tests;
   `/api/metrics` shape assertions; Playwright dashboard spec checks the per-core
   count equals `cpu.cores`, load averages render, and the unavailable-temperature
   note is shown when `temperatureC` is null.

## Risks

- Temperature discovery is hardware-specific; the VM has none. The UI must make
  that obvious rather than showing 0 °C.
- A 200 ms second sample adds a little latency to the 5 s collector; it is
  bounded and only runs in the background collector.
- `cores` remains the logical processor count (existing contract); per-core
  entries use the same numbering.
