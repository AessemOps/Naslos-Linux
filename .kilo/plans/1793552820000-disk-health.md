# Disk health (SMART + ZFS) for 0.3.1

Status: proposed · Target release: **0.3.1** (Naslos-Linux and Naslos-Installer
version parity)
Repos: `Naslos-Linux` (agent, API, chart, UI, image, spec/docs). The installer
only takes the 0.3.1 version bump and embeds the released pack.
Chosen scope: **SMART per disk plus the existing ZFS vdev state/error data, on a
dedicated per-disk health page**, with notifications.

## Decisions (confirmed)

| # | Decision |
| --- | --- |
| D1 | SMART is **read-only**: no `smartctl -s on`, no self-test scheduling, no device writes. |
| D2 | The privileged **agent** runs smartctl. No new DaemonSet, sidecar service or exporter. |
| D3 | Bundle a **pinned, static smartctl** in the agent image and mount the host `/sys` read-only (Talos has neither smartctl nor a SMART API). |
| D4 | Keep `GET /api/disks` (the Disk Setup wizard) stable; add a separate `GET /api/disks/health` and a `/disks/health` page. |
| D5 | Reuse the existing notification events `disk_failure` and `zfs_health`; do not add a new event type. |
| D6 | Unsupported/unavailable SMART is **not an error**: the API and UI report `available:false` with a reason (the VM's virtio disks exercise this path). |

## Facts that constrain the design (verified in code)

- Talos does **not** bundle smartctl and its `block.DiskSpec` has no SMART field
  (`pkg/machinery@v1.14.0/api/resource/definitions/block/block.pb.go:535`);
  SMART must come from the host devices.
- The agent is already privileged, host-networked and mounts the host `/dev`
  (`charts/naslos/templates/agent-daemonset.yaml`); it can run a smartctl binary
  from its own image against those device nodes. It does **not** mount `/sys`
  today; smartctl needs it for device/bridge detection.
- The agent runtime is `scratch` with only a static busybox
  (`agent/Dockerfile.rust`), so smartctl must be static (or copied with its musl
  loader/libs); it cannot use the Talos host's binaries.
- The pool page already renders vdev state, read/write/cksum and scan/errors
  from `zpool status` (`rust/agent/src/zfs/operations.rs:466`,
  `ui/src/routes/pools/[name]/+page.svelte`). Reuse that parser; do not
  re-implement ZFS parsing.
- `health_watch.rs` already polls pools every 60 s and notifies on transitions
  with `zfs_health`/`disk_failure`. Extend the same watcher for SMART/threshold
  transitions.
- `GET /api/disks` is a bare array used by `DiskWizard.svelte`; changing its
  shape would break the wizard. The new endpoint keeps it additive/separate.
- The agent's API is authenticated with the shared bearer token; every new
  route must sit behind the same auth layer (`rust/agent/src/server/mod.rs`).

## Architecture

### 1. Agent: smartctl runner and endpoint

New `rust/agent/src/smart.rs` (or `zfs/smart.rs` if it needs `host_root`):

- `SmartClient` runs `/app/smartctl --json=o -n standby -a <device>` directly
  (not through `chroot /host`) with a bounded timeout (default 10 s) and a
  bounded concurrency (4) over at most 64 whole disks.
- Enumerate whole disks with the existing `is_whole_disk` rule (skip
  partitions, loop, sr, zram); never accept a caller-supplied device path.
- Parse smartctl's JSON regardless of its exit code (smartctl returns a bitmask,
  and a failing disk is data, not a command failure). If the JSON cannot be
  parsed, return `available:false` with the stderr text as `message`.
- `-n standby` means a sleeping disk is **not** woken; report
  `standby:true`/`health:"UNKNOWN"` instead.
- Cache the full report for 30 s so the UI poll and the 60 s health watcher do
  not run smartctl twice.
- Map ATA/SATA, NVMe and SCSI fields; ATA wear uses attribute 177/233 when
  present, NVMe uses `percentage_used`; omit fields the device does not report.
- Map ZFS: flatten the existing `PoolHealth.config` tree (canonicalizing
  `/dev` names) and attach `{pool, vdev, state, readErrors, writeErrors,
  cksumErrors}` to the matching disk. If ZFS is unavailable, omit it.

Agent route (auth required): `GET /api/v1/disks/health`

```json
{
  "smartctlAvailable": true,
  "disks": [
    {
      "device": "/dev/sda",
      "smart": {
        "available": true, "enabled": true, "health": "PASSED",
        "temperatureC": 34, "powerOnHours": 12345, "wearPercent": 4,
        "reallocatedSectors": 0, "pendingSectors": 0,
        "uncorrectableSectors": 0, "mediaErrors": 0, "errorCount": 0,
        "standby": false, "message": ""
      },
      "zfs": {
        "pool": "tank", "vdev": "mirror-0", "state": "ONLINE",
        "readErrors": 0, "writeErrors": 0, "cksumErrors": 0
      }
    }
  ]
}
```

`smartctlAvailable:false` is a 200 response with ZFS-only entries; only an agent
outage or auth failure is an error. `SMARTCTL_BIN`, `SMARTCTL_TIMEOUT_SECONDS`
and `SMARTCTL_MAX_DISKS` are agent env vars (chart values with defaults).

### 2. API: merge and endpoint

New `GET /api/disks/health` (owner router, same auth as `/api/disks`):

- Call the agent endpoint, then merge with
  `TalosClient::get_discovered_volumes` (model/serial/size/type/system disk),
  `pool_members`/pool health (pool membership) and the existing disk
  signatures. The union includes disks the agent found but Talos did not.
- Response: `{smartctlAvailable, error, disks:[{device, model, serial, type,
  size, isSystemDisk, inPool, signatures, smart, zfs}]}`.
- If the agent is unreachable, return the Talos metadata with
  `smartctlAvailable:false` and a non-fatal `error` string (the page still
  shows disk inventory). If the agent reports `smartctlAvailable:false`, pass it
  through.
- Keep `GET /api/disks` unchanged (the wizard's contract).

### 3. UI: per-disk health page

- New route `ui/src/routes/disks/health/+page.svelte` and a sidebar item
  `Disk Health` (`/disks/health`, after `Disks`); a link/tab from the Disk Setup
  page points to it.
- Summary cards: total, healthy, warning, failed, SMART unavailable.
- Table sorted by severity (FAILED/FAULTED, DEGRADED/temperature/wear,
  UNKNOWN/unavailable, OK):
  device, model/serial, type/size, pool/vdev, ZFS state + read/write/cksum,
  SMART health, temperature, power-on hours, wear, reallocated/pending/
  uncorrectable/media errors, message.
- Badges: green PASSED/ONLINE, amber DEGRADED/temperature/wear warning, red
  FAILED/FAULTED/OFFLINE/UNAVAIL/REMOVED, grey unavailable/standby.
- Rows with a pool link to `/pools/<pool>`; refresh button and 60 s auto-refresh;
  "SMART unavailable on this disk" with the reason; an agent-unreachable banner.
- No new dependencies; use the existing Tailwind classes and `parseJsonSafe`
  pattern from `DiskWizard.svelte`.

### 4. Notifications

Extend `health_watch.rs` with a pure `disk_alerts(&[DiskHealth], thresholds)`
function (unit-tested) and transition tracking keyed by `disk:<device>`:

- `smart.health == FAILED` → `disk_failure` (error).
- `smart.temperatureC > DISK_HEALTH_TEMPERATURE_C` (default 55) →
  `zfs_health` (warning).
- `smart.wearPercent >= DISK_HEALTH_WEAR_PERCENT` (default 80) →
  `zfs_health` (warning).
- ZFS vdev `FAULTED|OFFLINE|UNAVAIL|REMOVED` → `disk_failure` (error);
  `DEGRADED` → `zfs_health` (warning).
- Recovery of a previously alerted key sends one warning; repeated polls do not
  repeat. Pool-level and disk-level transitions are tracked separately (a
  failed vdev may produce one pool and one disk notification, each once).
- `DISK_HEALTH_ENABLED=false` disables only the disk alerts; the page still
  works. Reuse `HEALTH_INTERVAL_SECONDS` for the poll.

### 5. Chart and image

- `agent/Dockerfile.rust`: build a static smartmontools `smartctl` from a
  **pinned tarball + sha256** in the builder (musl; verify with
  `file`/`ldd`/`--version`), copy it to `/app/smartctl`. Fallback if the static
  build fails: copy the Alpine `smartctl` plus the musl loader and the
  `libstdc++`/`libgcc` libs into the scratch root (still pinned).
- `agent-daemonset.yaml`: add a read-only `hostPath: /sys` volume/mount and the
  `SMARTCTL_*` env vars. The agent stays privileged; no new RBAC.
- `values.yaml`:
  ```yaml
  agent:
    smartctl:
      enabled: true
      timeoutSeconds: 10
      maxDisks: 64
  diskHealth:
    enabled: true
    temperatureWarningC: 55
    wearWarningPercent: 80
  ```
  The API deployment renders `DISK_HEALTH_*`; the agent renders `SMARTCTL_*`.
- `CREDITS.md`: smartmontools (version, GPL-2.0-or-later, upstream URL), bump
  `Last reviewed`.
- `scripts/audit.sh`: assert the Dockerfile pins the smartmontools version/sha,
  the runtime copies `/app/smartctl`, the DaemonSet mounts `/sys` read-only, and
  the chart renders the env vars.

## Security and safety

- smartctl is invoked with fixed arguments and a device path discovered from
  `/dev`; no user-controlled argv.
- The agent endpoint is behind the existing bearer token; the API endpoint is
  owner-only.
- SMART is read-only; no `-s on`, no `-t`, no `-X`.
- `-n standby` prevents waking sleeping disks; `-a` never writes.
- Bounded disk count, per-disk timeout and concurrency; a hung device cannot
  block the agent's other routes (spawned per request with a timeout).
- A failing disk is reported as data, not as an agent failure; the pool health
  watcher remains the source for pool-level state.

## Risks / open questions

- **Static smartctl build**: musl/static builds of smartmontools can be finicky;
  the fallback is the Alpine binary plus the musl loader/libs. The Dockerfile
  build must fail if the binary is not runnable/static.
- **Device coverage**: USB bridges and RAID controllers may need `-d` overrides;
  v1 reports them as unavailable rather than guessing.
- **ATA wear mapping**: attribute 177/233 is vendor-specific; omit rather than
  invent a percentage when the attribute is absent.
- **VM drill**: virtio disks have no SMART; the live test proves the graceful
  unavailable path, not real SMART values.
- **Notification duplication**: a failed vdev can produce a pool notification and
  a disk notification; both are transition-only. Confirm this is acceptable.
